# Decision: TTLock on-premise deployment

- **Date:** 2026-11-21
- **Status:** Proposed — blocked on a TTLock quote; awaiting owner sign-off
- **Task:** 34
- **Decision owner:** Luis
- **Reopens if:** we receive a quote, or a contract requires EU-only data processing

## Question

Should the pilot, or a later scale-up, run TTLock's paid on-premise deployment
instead of the cloud API, to remove the call quota, keep all lock data on our
own servers, and meet EU data-residency requirements?

## What is known

TTLock's on-premise guide describes three paid options
([On-premise solutions](https://euopen.ttlock.com/document-pages/en/userGuide/onPremise)):

1. **Solution 1:** we keep our app and API and integrate TTLock's JAR, gateway
   server package, Android/iOS SDKs, and card-encoder DLL.
2. **Solution 2:** TTLock supplies the app, web, server, and API; we supply the
   server.
3. **Solution 3:** TTLock supplies source code; we own the development.

What the guide states:

- All data, passwords, and eKeys are generated and stored on our server. No data
  is stored on TTLock's server, and the gateway connects to our local server
  through TTLock's gateway server package.
- It names the EU as a target scenario for data-security requirements.
- The server baseline is Linux, **6 GB+ RAM**, **100 GB+ disk**, Tomcat 8.5,
  **MySQL 5.6**, Redis, and **JDK 1.8**.
- It is **not a one-to-one copy of the TTLock App**. Missing features include
  wireless keypads, standalone door sensors, the G6 Matter gateway, and
  water/electricity meters.
- Support is free for one month after deployment, then an annual fee. Support
  hours are Beijing business hours, with online-only support abroad.
- Quotations are by WeChat (`ttlockdev`); **no public price list exists**.

## Cost

The TTLock licence fee is **not public and no quote has been requested yet**.
Until it is, this section is a framework, not a comparison.

Estimate the annual cost as:

```text
on-prem annual = licence + setup + (hosting + backups + monitoring) × 12
               + (ops hours per month × hourly rate) × 12
               + annual support fee
cloud annual   = upgraded developer plan price at the expected call volume
```

Planning ranges for the self-hosted part (estimates, not quotes):

| Item | Range per month |
|---|---|
| EU VM meeting 6 GB / 100 GB, with snapshots | €25–60 |
| Monitoring, log storage, off-site backup | €10–25 |
| Ops: patching, MySQL/Redis upkeep, on-call | 2–6 hours |

Two cost facts already work against it:

- The cloud free tier is **30,000 calls per month per application**
  ([FAQ](https://euopen.ttlock.com/document-pages/en/example/FAQ)). A pilot is
  unlikely to exceed it after Task 32 removes polling.
- The documented server stack (MySQL 5.6, JDK 8, Tomcat 8.5) is end-of-life.
  Running it in production adds security patching or an early upgrade path that
  TTLock has not documented.

## Data residency

On-premise is the **strongest residency option** in principle: TTLock states no
data reaches its servers. That directly supports the GDPR and LOPDGDD
commitments.

Unconfirmed, and required before any go:

1. Does the JAR or gateway server package contact TTLock for licence checks,
   telemetry, or updates? If yes, what data and where?
2. Where do backups live, and who can access them?
3. Does TTLock's support access require sharing production data?

## API compatibility

The current provider assumes a base URL and a bearer token. **The on-premise
model is not a drop-in replacement:**

- The on-premise server has its own API. TTLock's on-premise upgrade endpoints
  authenticate with a `secret` issued by TTLock, not the cloud `accessToken`
  (visible in the OpenAPI spec for the `*OnPremise` operations).
- TTLock's FAQ states that lock data generated by the open-platform SDK **cannot
  be used** with the on-premise server JAR
  ([FAQ, Integration 6](https://euopen.ttlock.com/document-pages/en/example/FAQ)).
  Locks would need re-initialisation against the local server.
- Passwords and eKeys are generated locally, so the guest-link flow becomes our
  own key-issuing service rather than a cloud API call.

A migration therefore needs a **second provider adapter**, not a URL change, plus
a lock re-enrolment plan. The domain logic in `lib/lockers` and `lib/shares` can
stay if the provider interface holds.

## Hardware support

Unconfirmed:

- Whether existing gateways can be re-pointed to our local server, or need new
  firmware or replacement.
- Whether the G6 Matter gateway is unsupported on-premise, as the feature list
  suggests.
- Which lock models are certified for the on-premise path.

This must be answered before a pilot purchase.

## Recommendation

**No-go for the pilot. Revisit only when a quote and a residency requirement
exist.**

Reasons:

1. The cloud free tier is sufficient for a pilot once Task 32 removes polling.
2. The licence cost, gateway migration, lock re-enrolment, and end-of-life
   server stack are large unknowns against a saving that may be zero at pilot
   scale.
3. It adds an operational burden (database, Redis, patching, on-call) that a
   small pilot should not carry.

The case becomes real if a client or tender **requires** EU-only processing with
no vendor cloud. In that situation on-premise is a sales enabler, and the cost is
justified by the contract rather than by API savings.

## What would change this decision

- A TTLock quote whose total annual cost is below the upgraded cloud plan at the
  expected volume.
- A signed requirement for no vendor-cloud processing.
- Evidence that gateways re-point without replacement and locks re-enrol without
  a site visit.

## Open questions for TTLock

1. Licence and setup price, and what the annual support fee covers.
2. Any outbound connection from the JAR or gateway package, and the data it sends.
3. Gateway compatibility and re-pointing procedure.
4. Supported lock models, and whether the G6 Matter gateway works on-premise.
5. Whether the end-of-life components (MySQL 5.6, JDK 8, Tomcat 8.5) can be
   replaced with supported versions.
